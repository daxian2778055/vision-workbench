**审核开始时有两个红点，均已定位处理：**

1. `RoundAbortSummaryTest::abortedSubFlowIsNotReportedAsFailure` 在 `-j 4` 下间歇红。
   单跑 3 次全过 ⇒ 时序脆弱，非产品缺陷。根因：腿靠固定 `qWait(300)` 卡进
   `m1` 的 600 ms 延时窗口，并行负载抖动会错过。中途曾改成「轮询等 `memberStarted`」，
   但该标志在 `nodeExecuted`（m1 **执行完**）才置位，等于等流程跑完再停，反而写出
   正常汇总行（`after=2 / before=1`）。**最终修法**：把 `m1` 延时放宽到 2000 ms
   作为稳定窗口、保持固定短等待；`memberStarted` 改 `std::atomic<bool>` 消除
   worker/GUI 跨线程读写竞争。修后 3 次并行全绿。
2. `eol_shape_gate` 报 `tool_written=210 expected=205`。核对：tracked 无增删（719=719）、
   blob 无 `CRLF→LF` 变化，是**工作树里 5 个既有文件的行尾形状被编辑工具写成 LF**。
   按闸契约应回正而非重冻结：回正 3 个测试文件 + 2 个 docs 后恢复 205=205。
   第 3 个 docs 本就在 205 白名单内，未动。

## 四、口径定案：按官方实施选项②（2026-11-09）

**取证**：`docs/VM4.4高精度匹配对齐规范.md:68` 明确写「排序类型 | 多目标时
**「当前结果」**的排序依据」。即主标量字段必须跟随排序后的第一条命中；用户新写的
多模板合并路径也已用 `merged.first()` 重写主字段。原单模板路径恒取第一实例（最高分），
`sortType = 0`（默认按分数降序）时两者恰好相同，`sortType != 0` 时与列表首行错位。

**落地**（不改变默认路径行为）：

- `MatchHit` 增加 `subpixX/subpixY`，append 时写入该命中自身的亚像素偏移——
  避免「主字段跟随排序后首条」时仍只留第一实例的 `bestSubpix`。
- 主字段段引入 `current = hits.first()`：`col/row/subX/subY/score/angle/scale/scaleY/cross`
  全部取自它；`mapAnchorToImage`、轮廓点映射、`MeasureResult` 同步改用这些值。
  `hits.first().row/col` 与原来的 `bestLoc + bestCenterInWarp + searchRect` 完全同源，
  **故默认 `sortType=0` 行为零变化**。
- 未动 `matchStatus` 的「是否达标」语义与超时判断（属整体状态，不属「当前结果」）。

**腿**：`templateCurrentResultFollowsSortType` 构造「最高分目标在下方、
`sortType=3`（按Y升序）首条在上方」，断言 `matchRow` / `matchScore` 与列表首行同源。

**改坏自证**：把 `current` 临时置空（等同旧实现），腿红且信息精确——
`matchRow=364.002，列表首行 row=124（旧实现会取最高分的下方目标）`；还原后 71 passed。

## 五、需确认但不构成当前缺陷

- `collectSearchValues` 在 `maxCount <= 1` 时有潜在除零；当前所有调用点传 90 或 16，产品路径不可达。
- `maskRegionFromData` 只 `cv::threshold` 不统一 `CV_8U`，混合深度掩膜与 `bitwise_and`
  可能触发 OpenCV 类型断言；`catch (HException&)` 空处理吞掉 Region 失效原因。
- 精修阶段 `search` 是局部窗口，而图像型 ROI 过滤要求 `roiMask.size() == search.size()`
  ⇒ 精修阶段的 ROI 过滤被静默跳过（既有 r19 路径残留）。
- 直接 `node.run(false)` 会绕过 `normalizeRuntimeParams()`；产品 `process()` 路径有两道钳制，正常。
- 部分新增腿只测静态辅助函数 / ParamSpec 默认值（如整数化并列规则、内容指纹），
  不是产品行为腿；已在各自注释里标明性质。
