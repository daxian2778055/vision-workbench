## 1. 六项悬项逐条回执

### 1.1 写闸升起时是否停止当前流（客户报告 P0-1②）

- **报告原述**：写闸在流程已运行中升起后，既有流程可继续跑；建议「停止当前流，或至少拒绝新一轮／新触发（二选一，产品拍板）」。
- **册内登记位**：附表第一百九十二条（切片 B 收束与该族终态）、一百九十八条（触发面线程前提钉死与 P1 章结）。
- **当前实测**：运行闸＝已登录且写闸未开（会话面与执行器侧同判据）；**新一次运行发起已被闸拒**（七处启动入口与单算子执行位与下游重算位同口径）；已在跑的流程不经过该判定（产线不停线口径，写在会话面注释与拍板行里）；写闸的失败关闭语义在案（只有明确读到「出厂口令已停用」才放开，读不到按未停用处理）。
- **拍板结论**：**维持现状——闸拦新发起，既有流不停**。「停当前流」这一半不做。
- **依据**：停流会打断在制品与在产节拍，属产线策略而非安全缺口；安全缺口在「闸开后仍能发起新跑」那一半，而那一半已闭合。把闸做成硬停流是可用性代价明显大于安全收益的动作。
- **后续轮次**：无（登记为产品取舍；若日后现场要求，另立行为变更轮）。

### 1.2 通信监听默认是否收紧为回环（客户报告 P1-3）

- **报告原述**：TCP 绑 `Any:502`、UDP 绑 `AnyIPv4`、Modbus 仅端口维度；建议「默认回环或强制显式绑定地址」。
- **册内登记位**：附表第一百四十四条（三类服务端全网卡监听登记为产品级取舍）、第一百七十七条（通信监听地址配置面落地）、第二百一十九条（客户改口径：监听地址收紧为必填）。
- **当前实测**：三类服务端绑定面统一走一处解析（**空参＝未配置＝拒启动**，第二百一十九条；**显式必须是 IP 字面量**并原样绑定，确实要全网卡写 0.0.0.0 即明示；无效一律拒启动，不静默回落扩面；显式全网卡落日志）。原先的「静默 Any」已消除，「留空＝全网卡」这条默认面亦已撤掉。
- **拍板结论**：**不收紧为回环，维持全网卡默认**；已在配置面显式化。⚠️ **就地补证（原文保留）**：本条的默认面已由客户在 U-202 期改口径——收紧为**必填**（留空＝未配置＝三处同形拒启动并留可执行提示），未取「默认回环」；第二百一十九条为现行结论。
- **依据**：现场接入以隔离网段为主，收紧默认会打断既有接入且收益取决于部署侧网段是否真的隔离；显式化＋无效拒启动已把「悄悄扩面」这一半关掉。
- **后续轮次**：**文档动作**——在安全指南补一条「通信监听地址必填，默认面已撤（留空＝未配置＝拒启动）」（原文写的「通信默认全网卡，隔离靠网段与显式绑定」随第二百一十九条作废）；下轮随未加密包那条一并补。

### 1.3 根目录三枚墓碑文件是否迁出（客户报告 P2-8）

- **报告原述**：`requirements_decoded.txt`、`需求.txt`、`diag-churn.txt` 仍在根目录；建议删除或归档出仓库根。
- **册内登记位**：附表第一百六十二条（两枚自刻墓碑、一枚压测产物副本，按「旧行一字节不动」冻结原地）。
- **当前实测**：根目录 tracked 三枚 ＋ 各自的墓碑/废弃注记在位（需求.txt 自注「已迁移，请勿直接编辑」；requirements_decoded.txt 自注「不可恢复，已废弃」并带废弃日期；diag-churn.txt 为压测回归产物副本）。三者的引用面在册内已被点名。
- **拍板结论**：**维持原地**，不迁出、不删除。
- **依据**：迁出会断既有引用（册内与文档里的指路语），而这三枚要么已自刻墓碑（读者进得去、看得懂），要么是产物副本；删除的净收益只是仓库根好看一点。
- **后续轮次**：无（登记为产品取舍）。

### 1.4 未签名明文方案是否要求签名或首次执行确认（客户报告 P1-1①）

- **报告原述**：未签名明文 `.vfp` 可加载，`filePath` 等路径无限制；建议「对未签名明文包的首次脚本执行做签名校验或显式确认」＋路径 jail。
- **册内登记位**：附表第一百七十九条（方案内文件路径限位三面落地）、第一百九十五条（挂账项复审对账：路径限位已落、签名与 MAC 未落）、第二百二十一条（旧明文打包在真加载入口拒收）。
- **当前实测**：路径侧已闭合（方案内相对路径锚定方案目录；目录外绝对路径载入须显式确认，未确认即拒载——第二百一十七条；执行侧解析位统一漏斗）。脚本侧实测：解释器路径钉死（同目录同名 exe 不可顶替）＋容器沙箱准备失败即拒。**分享件面的完整性位已收口**：v2 明文打包带 HMAC、加密信封带口令派生 MAC、**旧 v1 明文打包（无完整性位）自第二百二十一条起在真加载入口拒收**；**作者签名仍无**（按下一行拍板不做）。方案内文件（`.vfp` 裸 JSON）是本机在用文件、不在分享面，仍无完整性位——这一点不隐瞒。安全指南现无「未加密包」一条。
- **拍板结论**：**不引入包级签名**（签名要密钥管理，超出当前产品形态）；未加密包的剩余风险是「明文外发即泄露」，属部署侧纪律而非代码缺口。⚠️ **就地补证（原文保留）**：客户在本轮改口径——「无完整性的旧明文打包」不再照收（176 行的「照常收下 ＋ 置缺位注记」随之作废），改为**真加载入口拒收**并留可执行提示（请用带完整性位的新格式，或由旧版本打开后另存为新格式）；包级签名仍按本行拍板不做。
- **依据**：脚本侧两道面（路径钉死与沙箱拒启）＋路径限位三面已把「恶意包能直接被跑」这一层关掉；剩下的明文泄露用部署纪律管比引入一套密钥体系便宜得多。
- **后续轮次**：**文档动作**——安全指南补「未加密包不得外发／不得用于跨现场分发」（下轮一并补）。

### 1.5 终局中止撤除后的对外语义（切片 C 立项书未决 O-2）

- **报告原述**：执行器析构路径上硬中止不利于优雅退出与问题定位；建议改为可观测错误日志＋有序停线程。
- **册内登记位**：附表第一百七十八条（析构中止软化为两段有界等待）、第一百九十四条（切片 C 立项书）、第二百零三条（float 缺陷修轮所在轮次上下文）。
- **当前实测**：终局中止已软化为两段有界等待（一段 5 秒、二段 15 秒，二段前重停一轮）＋应用层收尾钩子＋**仍以中止进程收尾**；源件注释自指「全砍中止需全核共享所有权化重设计」。终局之所以必须硬，是因为工作线程仍会读执行器主体。
- **拍板结论**：撤除中止的对外语义取「**中止该执行器并进入可观测终态**（停流程、记终态、现场可见的失败提示），进程不中止」；中止进程只保留为最后一道不可达兜底。
- **依据**：产线不应因单个执行器卡死而整进程陪葬；终态可见＋提示在场，现场能处置；而「工作线程不再读执行器主体」的前置由 P2／P3 两期解决。
- **后续轮次**：**P4 期**（依 P2 与 P3 的落地情况启；届时带红绿臂与座）。

### 1.6 节点壳与非对象状态体分离是否可接受（切片 C 立项书未决 O-1）

- **报告原述**：客户报告 P2-6 巨型类项的根因是执行器与图形状态的所有权；共享所有权化是终局方向。
- **册内登记位**：附表第一百九十四条（立项书）、第一百九十六条（P0 所有权契约护栏）、第一百九十七条与第一百九十八条（P1 期预研与章结：P1 取消，其内核并入 P2 与 P3）。
- **当前实测**：执行器侧裸指针九族（场景指针、缓存键三族、图索引两族、执行队列与集合族、账簿键、节点归属指针、触发注册、全局单例）；其中单例与归属指针两面为**工作线程读、界面线程写**的跨线程悬垂面（弱引用非线程安全、代次号只能检出不能阻止解引用、正解是共享控制块）；节点为 QObject 派生且与父子树同生共死。
- **拍板结论**：**接受「QObject 壳 + 非对象状态体分离」**，并据此启动 **P2 期**（路线取**分层共享**：场景持节点强引用、执行器只持共享的快照与存活控制块；不做全量 QObject 化）。
- **依据**：执行期只读状态不必过信号槽，壳与状态体分离是可行且常规的做法；分层共享能把「解引用期安全」一次性解决，而全量共享化会一次改动全部算子类与端口与连线件，回归面过大。
- **后续轮次**：**P2 期**（下一轮出设计面：共享控制块的形状与取锁序与快照持有期与墓碑 flush 的线程归属，逐项先量后定；每期独立轮、红绿臂、座双注册、宿主整轮）。
