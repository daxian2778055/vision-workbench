## 二、本轮修掉的 4 项（确定性、改动可控，均带腿）

### 1. gtd 导入半残文件会静默清空全部现场通信配置（最严重）

`CommunicationManagerDialog.cpp:227-247` 旧版只校验 `format`。
`{"format":"visionflow-communication"}` 这种半残文件会通过校验，
随后 `CommunicationManager::fromJson({})` **无条件清空**设备/接收事件/发送事件/响应配置，
`GlobalTriggerManager` / `HeartbeatManager` 同样被清空 —— 用户点一次「导入」就丢光配置。

修法：
- 校验 `version == 1`；
- 三个顶层块必须存在且各自的数组键是 array（`devices` / `receiveEvents` / `sendEvents` /
  `triggers` / `heartbeats`），**在动任何配置之前**拒收；
- 按钮入口 `onImportGtd` 加整包覆盖确认（`QMessageBox::question`，默认 No）；
- 导出改 `QSaveFile` 原子写并检查实际写入字节数，防止半截文件反过来毒害导入。

腿：`tests/comm_writeback_test.cpp` 在既有 gtd 腿里补 4 种半残载荷，
断言全部拒收且 `GTD_DEV` 仍在。

### 2. FINS/TCP 正常分片被当成脏帧清空（真机会永久失步）

`FinsFrame.cpp:64-73` 旧版 `parseTcpHeader` 要求缓冲 ≥20 字节、
且 `len <= buf.size()-4`。这把**长度合法但数据未收齐的正常半包**判成解析失败；
`FinsCommNode.cpp:251-258` 随即清空整段接收缓冲。真机 TCP 分片下链路反复超时重连。

修法：帧头 16 字节即可解析；只校验长度上界（1 MB），
「是否收齐」完全交给调用方用 `headerBytes > m_rxBuffer.size()` 判断；
调用方脏帧判定阈值同步改为 16 字节。

腿：`tests/fins_test.cpp` 更新旧语义断言（长度仅比缓冲大不再算非法），
新增「只收到 16 字节帧头」与「短 1 字节」都能解析且 `headerBytes` 正确的断言。

### 3. 子界面圆角保存后丢失

`RuntimeInterface.cpp:331-339 / 515-525` 的 `cornerRadius` 只在 `RunStatus` 分支读写，
而 `RuntimeInterfaceDesigner.cpp:2386` 允许给 `SubInterface` 设圆角、
`RuntimeInterfaceView.cpp:1350` 会用它 ⇒ 保存后变回 0。

修法：toJson/fromJson 改成 `RunStatus || SubInterface` 共用，保留 0..40 钳制。

腿：`UiGuardsTest::subInterfaceCornerRadiusRoundTrips`（含 RunStatus 钳制回归）。

### 4. 撤销快照漏了第三层隐式共享 + 定时器收口

`pushUndo()`（B1f）只 detach `pages` 和 `pages[].controls`，
但 `RuntimeInterface::subPages` 也是隐式共享容器，`effectivePage()` 返回其中元素的裸指针 ——
子界面编辑态下同样会污染快照。

修法：抽出 `detachLayoutSnapshot()` 统一做三层 detach（含 `subPages` 及其 `controls`）；
`undo()/redo()` 停止挂起的 600ms 属性合并定时器。

**一次自我纠错**：我最初在 `undo()/redo()` 里也调了 `detachLayoutSnapshot`，
结果 `UiGuardsTest` 在 `-j 4` 下稳定访问违规（`0xC0000005`，崩在 `invokeMethod("undo")`）。
对照实验关掉该句后单腿连跑 **5/5 通过**，恢复用户原逻辑后两次全量并行 80/80。
原因想清楚了：**快照在 `pushUndo()` 入栈时已彻底自持，取出时无需再 detach**，
那两处是我过度修复。代码里留了注释记录这次实验，避免以后又加回去。

### 1. 设备删除/重命名的悬空引用

取证发现一个必须避开的陷阱：`CommunicationManager::removeDevice(name)` 还被
「配置设备→确定」当作 **remove + add 同名重建** 用（`CommunicationManagerDialog.cpp:840/869/879`）。
若在 `removeDevice` 里无条件清理引用，用户每改一次设备参数就会连带删光该设备的
事件、心跳与响应配置——属于灾难性回归。

因此用带默认值的参数区分两种语义：

- `removeDevice(name, bool cleanupReferences = false)`：默认 **false** 是重建路径，
  引用全部保留；
- 仅设备列表「删除设备」按钮传 **true**，清理：
  `HeartbeatManager::unregisterHeartbeat(name)`、引用该设备的接收/发送事件、
  响应配置三个 section（`schemeLoad`/`flowControl`/`cameraResponse`）里指向它的 `device`。
  响应配置只清 `device`，保留 content/delaySec/enabled 等，用户只需重选设备。
- 删除确认框改为明确告知会影响事件/心跳/响应配置。
- `renameDevice` 补：**响应配置的 device 跟随改名**（原实现只跟了节点、事件、心跳、
  帧缓冲，改名后响应发送会静默失败）。

腿 `deviceRemovalCleansReferencesButRecreateKeepsThem` 三段覆盖：
①重建模式引用全在（防回归的关键臂）、②重命名后响应配置 device 变新名、
③主动删除后事件/心跳/响应 device 全清且 content 保留。

### 2. 撤销路径收口

- 8 个对齐/分布槽（`onAlignLeft/HCenter/Right/Top/VCenter/Bottom/HSpread/VSpread`）
  原本直接调 `alignSelected` 不压快照，一键排完无法回退。改为先判
  `selectedSet().size() >= 2`（少于 2 个 alignSelected 本就 no-op，不白压空快照），
  再 `pushUndo()`。用显式函数而非宏生成，避免锚点类脚本漏检。
- `loadLayout()` 加载整套新布局后，旧快照指向的是另一套页/控件，撤销回去既无意义
  也可能引用已不存在的页。改为停掉挂起的 600ms 合并定时器 + 清空 undo/redo 栈。

腿 `designerAlignCanBeUndone`：单选对齐不动几何、多选左对齐生效（并断言第二个控件
位置确实变了，防空转）、`undo()` 后恢复对齐前几何。

## 六、第三批：FINS 测试自证闭环拆解

**问题**：`fins_test.cpp` 里实现、期望、桩三者共用同一套被测函数——

| 位置 | 自证形式 |
|---|---|
| `L405-408` | 写帧期望由 `Fins::command()` + `Fins::writeMemoryParams()` 现造；组包改错，期望跟着变 |
| `L106` | mock 观测的「收到的节点地址请求」用 `Fins::tcpHeader()` **重建**，不是收到的原文 |
| `L352` | 该观测值又与 `Fins::nodeAddressRequest()`（被测函数）比较 |
| `L96 / L113 / L119 / L123` | mock 用 `Fins::parseTcpHeader/tcpHeader/frameSend` 拆帧造帧 |
| `L225` | 帧头解析腿的输入也由 `Fins::tcpHeader` 自造自拆 |

结果：协议组包口径写错时，实现和桩一起错，回环腿仍全绿。

**改法**：

- mock 侧新增**独立实现** `readBe32/appendBe32/mockParseTcpFrame/mockTcpFrame`，
  按公开报文格式逐字节读写大端字段，全程不调用 `Fins::*`。
- 节点地址请求的观测值改存 `state->buffer.left(headerBytes)`——**收到的原文**，
  期望改独立硬编码 `46494e53...`（W342 的 20 字节帧）。
- 写帧期望改独立硬编码 `80000200020000010000 0102 8200006400011234`，
  并在注释里逐字段说明 ICF..SID / MC / 区地址字数值。
- 帧头解析腿的输入也由 `mockTcpFrame` 构造。
- `L289/296` 的字节级腿保留：它们调 `Fins::command` 是**被测对象本身**，
  期望本来就是独立 hex，不属于自证。

**改坏自证**：临时把产品 `FinsFrame.cpp::command()` 的 DA1 写死为 0，
`FinsTest` 变成 `7 passed / 2 failed`——`loopbackFinsTcpRead()` 与
`loopbackFinsTcpWrite()` 都红。旧的自生成期望下写帧腿不会红（期望同步变 0），
这正说明新基线确实独立于被测函数。还原后 `FinsTest` 9 passed。

> 边界：这解决的是「测试能不能发现实现错了」，**不解决「规范本身是不是这样」**。
> 存储区参数字节布局是否符合 W342 仍需真机报文，该项继续挂起。

## 七、第四批：响应配置的终态与可观测性

**取证**：

- `MainWindow.cpp:2074-2077`：IDLE 只在 `FlowExecutor::executionFinished` 发。
  手动停止（`executionStopped`）、运行错误（`executionError`）、终局撤除
  （`executionAbandoned`）都只更新状态栏/日志，**PLC 会一直停在 BUSY**。
- `responseSent` 全仓**只有 `CommResponseManager.cpp:37` 一处 emit、零 connect**；
  发送失败只写 `VFP_DEBUG`，现场界面完全看不到。

**改法**：

1. `connectExecutorSignals` 里抽出 `reportIdle`（取执行器自己的流程名，不过滤后台流程），
   接到 `executionFinished` / `executionStopped` / `executionError` / `executionAbandoned`
   四类终态。忙碌仍由 `executionStarted` 上报。
2. `CommResponseManager` 增 `QSet<QString> m_busyFlows`，`handleFlowState` 改为**边沿语义**：
   重复 BUSY 吞掉、从没忙碌过的终态不凭空发 IDLE、多个终态连发只出一条 IDLE，
   下一轮可重新进入忙碌。这同时解决了「补全终态会不会重复发」的顾虑。
3. `MainWindow` 构造函数一次性连接 `responseSent` → `logMessage`，**只记失败**
   （避免每轮成功响应刷屏）。走 `logMessage` 而不是直接 `UiLogBus::publish`，
   以遵守「日志栏是唯一写入点」的既有约定，运行界面「界面日志」控件同步可见。

腿 `responseFlowStateIsEdgeTriggered`：无 busy 的 false 不发、busy 发 BUSY、
重复 busy 吞掉、终态发 IDLE、连发 3 个终态仍只有 1 条 IDLE、下一轮可重新进忙碌；
同时断言失败时 `responseSent` 的 `ok=false` 如实上报（设备故意不存在）。

> 边界：MainWindow 的终态接线本身没有自动化腿（构造主窗口成本高），靠代码审查 +
> 边沿去重腿覆盖核心行为。若现场要求可观测，可在通信监视器里加一列「最近响应结果」。
