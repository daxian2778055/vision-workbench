## 二、本轮修掉的 4 项（确定性、改动可控，均带腿）

### 1. gtd 导入半残文件会静默清空全部现场通信配置（最严重）

`CommunicationManagerDialog.cpp:227-247` 旧版只校验 `format`。
`{"format":"visionflow-communication"}` 这种半残文件会通过校验，
随后 `CommunicationManager::fromJson({})` **无条件清空**设备/接收事件/发送事件/响应配置，
`GlobalTriggerManager` / `HeartbeatManager` 同样被清空 —— 用户点一次「导入」就丢光配置。

修法：
- 校验 `version == 1`；
- 三个顶层块必须存在且各自的数组键是 array（`devices` / `receiveEvents` / `sendEvents` /
  `triggers` / `heartbeats`），**在动任何配置之前**拒收；
- 按钮入口 `onImportGtd` 加整包覆盖确认（`QMessageBox::question`，默认 No）；
- 导出改 `QSaveFile` 原子写并检查实际写入字节数，防止半截文件反过来毒害导入。

腿：`tests/comm_writeback_test.cpp` 在既有 gtd 腿里补 4 种半残载荷，
断言全部拒收且 `GTD_DEV` 仍在。

### 2. FINS/TCP 正常分片被当成脏帧清空（真机会永久失步）

`FinsFrame.cpp:64-73` 旧版 `parseTcpHeader` 要求缓冲 ≥20 字节、
且 `len <= buf.size()-4`。这把**长度合法但数据未收齐的正常半包**判成解析失败；
`FinsCommNode.cpp:251-258` 随即清空整段接收缓冲。真机 TCP 分片下链路反复超时重连。

修法：帧头 16 字节即可解析；只校验长度上界（1 MB），
「是否收齐」完全交给调用方用 `headerBytes > m_rxBuffer.size()` 判断；
调用方脏帧判定阈值同步改为 16 字节。

腿：`tests/fins_test.cpp` 更新旧语义断言（长度仅比缓冲大不再算非法），
新增「只收到 16 字节帧头」与「短 1 字节」都能解析且 `headerBytes` 正确的断言。

### 3. 子界面圆角保存后丢失

`RuntimeInterface.cpp:331-339 / 515-525` 的 `cornerRadius` 只在 `RunStatus` 分支读写，
而 `RuntimeInterfaceDesigner.cpp:2386` 允许给 `SubInterface` 设圆角、
`RuntimeInterfaceView.cpp:1350` 会用它 ⇒ 保存后变回 0。

修法：toJson/fromJson 改成 `RunStatus || SubInterface` 共用，保留 0..40 钳制。

腿：`UiGuardsTest::subInterfaceCornerRadiusRoundTrips`（含 RunStatus 钳制回归）。

### 4. 撤销快照漏了第三层隐式共享 + 定时器收口

`pushUndo()`（B1f）只 detach `pages` 和 `pages[].controls`，
但 `RuntimeInterface::subPages` 也是隐式共享容器，`effectivePage()` 返回其中元素的裸指针 ——
子界面编辑态下同样会污染快照。

修法：抽出 `detachLayoutSnapshot()` 统一做三层 detach（含 `subPages` 及其 `controls`）；
`undo()/redo()` 停止挂起的 600ms 属性合并定时器。

**一次自我纠错**：我最初在 `undo()/redo()` 里也调了 `detachLayoutSnapshot`，
结果 `UiGuardsTest` 在 `-j 4` 下稳定访问违规（`0xC0000005`，崩在 `invokeMethod("undo")`）。
对照实验关掉该句后单腿连跑 **5/5 通过**，恢复用户原逻辑后两次全量并行 80/80。
原因想清楚了：**快照在 `pushUndo()` 入栈时已彻底自持，取出时无需再 detach**，
那两处是我过度修复。代码里留了注释记录这次实验，避免以后又加回去。

### 1. 设备删除/重命名的悬空引用

取证发现一个必须避开的陷阱：`CommunicationManager::removeDevice(name)` 还被
「配置设备→确定」当作 **remove + add 同名重建** 用（`CommunicationManagerDialog.cpp:840/869/879`）。
若在 `removeDevice` 里无条件清理引用，用户每改一次设备参数就会连带删光该设备的
事件、心跳与响应配置——属于灾难性回归。

因此用带默认值的参数区分两种语义：

- `removeDevice(name, bool cleanupReferences = false)`：默认 **false** 是重建路径，
  引用全部保留；
- 仅设备列表「删除设备」按钮传 **true**，清理：
  `HeartbeatManager::unregisterHeartbeat(name)`、引用该设备的接收/发送事件、
  响应配置三个 section（`schemeLoad`/`flowControl`/`cameraResponse`）里指向它的 `device`。
  响应配置只清 `device`，保留 content/delaySec/enabled 等，用户只需重选设备。
- 删除确认框改为明确告知会影响事件/心跳/响应配置。
- `renameDevice` 补：**响应配置的 device 跟随改名**（原实现只跟了节点、事件、心跳、
  帧缓冲，改名后响应发送会静默失败）。

腿 `deviceRemovalCleansReferencesButRecreateKeepsThem` 三段覆盖：
①重建模式引用全在（防回归的关键臂）、②重命名后响应配置 device 变新名、
③主动删除后事件/心跳/响应 device 全清且 content 保留。

### 2. 撤销路径收口

- 8 个对齐/分布槽（`onAlignLeft/HCenter/Right/Top/VCenter/Bottom/HSpread/VSpread`）
  原本直接调 `alignSelected` 不压快照，一键排完无法回退。改为先判
  `selectedSet().size() >= 2`（少于 2 个 alignSelected 本就 no-op，不白压空快照），
  再 `pushUndo()`。用显式函数而非宏生成，避免锚点类脚本漏检。
- `loadLayout()` 加载整套新布局后，旧快照指向的是另一套页/控件，撤销回去既无意义
  也可能引用已不存在的页。改为停掉挂起的 600ms 合并定时器 + 清空 undo/redo 栈。

腿 `designerAlignCanBeUndone`：单选对齐不动几何、多选左对齐生效（并断言第二个控件
位置确实变了，防空转）、`undo()` 后恢复对齐前几何。

## 六、第三批：FINS 测试自证闭环拆解

**问题**：`fins_test.cpp` 里实现、期望、桩三者共用同一套被测函数——

| 位置 | 自证形式 |
|---|---|
| `L405-408` | 写帧期望由 `Fins::command()` + `Fins::writeMemoryParams()` 现造；组包改错，期望跟着变 |
| `L106` | mock 观测的「收到的节点地址请求」用 `Fins::tcpHeader()` **重建**，不是收到的原文 |
| `L352` | 该观测值又与 `Fins::nodeAddressRequest()`（被测函数）比较 |
| `L96 / L113 / L119 / L123` | mock 用 `Fins::parseTcpHeader/tcpHeader/frameSend` 拆帧造帧 |
| `L225` | 帧头解析腿的输入也由 `Fins::tcpHeader` 自造自拆 |

结果：协议组包口径写错时，实现和桩一起错，回环腿仍全绿。

**改法**：

- mock 侧新增**独立实现** `readBe32/appendBe32/mockParseTcpFrame/mockTcpFrame`，
  按公开报文格式逐字节读写大端字段，全程不调用 `Fins::*`。
- 节点地址请求的观测值改存 `state->buffer.left(headerBytes)`——**收到的原文**，
  期望改独立硬编码 `46494e53...`（W342 的 20 字节帧）。
- 写帧期望改独立硬编码 `80000200020000010000 0102 8200006400011234`，
  并在注释里逐字段说明 ICF..SID / MC / 区地址字数值。
- 帧头解析腿的输入也由 `mockTcpFrame` 构造。
- `L289/296` 的字节级腿保留：它们调 `Fins::command` 是**被测对象本身**，
  期望本来就是独立 hex，不属于自证。

**改坏自证**：临时把产品 `FinsFrame.cpp::command()` 的 DA1 写死为 0，
`FinsTest` 变成 `7 passed / 2 failed`——`loopbackFinsTcpRead()` 与
`loopbackFinsTcpWrite()` 都红。旧的自生成期望下写帧腿不会红（期望同步变 0），
这正说明新基线确实独立于被测函数。还原后 `FinsTest` 9 passed。

> 边界：这解决的是「测试能不能发现实现错了」，**不解决「规范本身是不是这样」**。
> 存储区参数字节布局是否符合 W342 仍需真机报文，该项继续挂起。

## 七、第四批：响应配置的终态与可观测性

**取证**：

- `MainWindow.cpp:2074-2077`：IDLE 只在 `FlowExecutor::executionFinished` 发。
  手动停止（`executionStopped`）、运行错误（`executionError`）、终局撤除
  （`executionAbandoned`）都只更新状态栏/日志，**PLC 会一直停在 BUSY**。
- `responseSent` 全仓**只有 `CommResponseManager.cpp:37` 一处 emit、零 connect**；
  发送失败只写 `VFP_DEBUG`，现场界面完全看不到。

**改法**：

1. `connectExecutorSignals` 里抽出 `reportIdle`（取执行器自己的流程名，不过滤后台流程），
   接到 `executionFinished` / `executionStopped` / `executionError` / `executionAbandoned`
   四类终态。忙碌仍由 `executionStarted` 上报。
2. `CommResponseManager` 增 `QSet<QString> m_busyFlows`，`handleFlowState` 改为**边沿语义**：
   重复 BUSY 吞掉、从没忙碌过的终态不凭空发 IDLE、多个终态连发只出一条 IDLE，
   下一轮可重新进入忙碌。这同时解决了「补全终态会不会重复发」的顾虑。
3. `MainWindow` 构造函数一次性连接 `responseSent` → `logMessage`，**只记失败**
   （避免每轮成功响应刷屏）。走 `logMessage` 而不是直接 `UiLogBus::publish`，
   以遵守「日志栏是唯一写入点」的既有约定，运行界面「界面日志」控件同步可见。

腿 `responseFlowStateIsEdgeTriggered`：无 busy 的 false 不发、busy 发 BUSY、
重复 busy 吞掉、终态发 IDLE、连发 3 个终态仍只有 1 条 IDLE、下一轮可重新进忙碌；
同时断言失败时 `responseSent` 的 `ok=false` 如实上报（设备故意不存在）。

> 边界：MainWindow 的终态接线本身没有自动化腿（构造主窗口成本高），靠代码审查 +
> 边沿去重腿覆盖核心行为。若现场要求可观测，可在通信监视器里加一列「最近响应结果」。

### 补充（同批）：`connectExecutorSignals` 里 19 处裸 `FlowExecutor*`

`MainWindow::connectExecutorSignals()` 内 19 个 lambda 捕获裸 `ex`，而 `ex` 由
`FlowExecutorToken`（`shared_ptr`）持有 —— 终局撤除路径下执行器可能先于**已排队**的
functor 调用销毁；sender 销毁只断开连接，不会取消已 post 的调用。

修法：函数开头建 `QPointer<FlowExecutor> exGuard(ex)` 统一守卫，19 处捕获改为 `exGuard`，
每个 lambda 首行 `if (!exGuard) return;`，体内 `ex->` → `exGuard->`、
`ex ==/!= m_executor` → `exGuard.data() ==/!= m_executor`。`reportIdle` 同样带守卫。

> 未补专门运行腿：构造「信号已排队 → 回收执行器 → 跑事件循环」需要真 QThread 执行器
> 与精确时序控制，收益低于成本；本批是纯防御性判空、行为不变，由现有 80 个套件
> （含执行链相关腿）做回归保障。

## 八、第七批（授权后）：子界面密码改摘要存储

用户 2026-11-11 授权「需要拍板的你也决定，项目还没上线」——**格式与语义都可以直接改，
不用背兼容包袱**。据此把审核清单里唯一明确标「需产品拍板」的一项定下来。

### 决定

| 项 | 原状 | 决定 |
|---|---|---|
| 密码存储 | 布局 JSON 里存**明文** `subPassword` | 改存 PBKDF2 风格摘要 `pbkdf2$<iter>$<saltHex>$<hashHex>`（SHA-256，20000 次迭代，16 字节随机盐） |
| 校验 | `input != subPwd` 字符串直接比较（非常量时间） | `verifySubPassword()`，**定长比较**：长度不同也不提前 return，不靠耗时泄露匹配长度 |
| 已存布局 | — | 读入时把明文**就地升级**为摘要。这不是「兼容旧项目」，而是避免用户自己开发机上已有的布局打不开子界面 |

### 实现要点

- 摘要三函数放 `RuntimeInterface.h/cpp`：`hashSubPassword` / `verifySubPassword` /
  `isHashedSubPassword`，与序列化同处，避免安全逻辑散落。
- 迭代次数上界校验（>1e6 直接拒绝）：防止有人手改布局文件塞个天文数字，
  打开子界面时卡死。
- 随机盐：同一密码两次摘要不同，避免「两个子界面密码相同」被人一眼看出。
- **设计器不改用户预期**：
  - 输入框**永远不回显摘要**（原实现 `setText(ctrl->subPassword)` 会把摘要显示出来）；
    改为占位提示「已设置（输入新密码可替换）」。
  - 写回从 `textEdited` 改为 `editingFinished`。这是个真坑：`textEdited` 每敲一个字符
    触发一次，如果在那里哈希，密码会变成「最后一个字符的摘要」。
  - 留空 = 不修改；要取消密码用新增的「清除」按钮，避免「留空」既表示不改又表示清除的歧义。

### 腿

`subPasswordIsHashedAndVerified` 八组断言：摘要格式可识别且不含明文、两次哈希不同（随机盐）、
正确/错误/空密码、未设置密码放行、**摘要被改一位必须失败**（证明真的在比对）、
迭代次数超上界直接拒绝（不卡死）、**明文迁移后旧密码仍可校验**、布局往返保留摘要。

顺带修正两条既有腿：`subInterfacePagesRoundTripAndDepth` 与 `b3NewControlsRoundTrip`
原本断言 `subPassword` 明文等值往返，现在改为断言「是摘要 + 原密码可校验」。
腿红了正好说明它确实在测这个字段，不是摆设。`UiGuardsTest` **62 passed**。

### 我决定「不动」的项及理由

| 项 | 决定 | 理由 |
|---|---|---|
| FINS 存储区字节布局 | **不动**，等真机报文 | 唯一可能让协议完全不通的点，但没有依据地改比不改更危险；`fins_test` 已拆自证闭环，等报文到位能快速验证 |
| 撤销剩余的 B3 属性 lambda / 子界面属性 | 延后 | 与密码无关，属另一主题；混在一批里会让回归难定位 |
| `RegisterSpaceBar` 清空不可撤销 | 延后 | 同上，且需要先定「清空」的撤销粒度（整表一次 vs 逐格） |

## 九、第八批（授权后）：属性面板撤销统一收口

第七批之后继续按「撤销语义完整性」推进——工具条「撤销」是 VM 1:1 的明确项，
但面板上一半的编辑根本进不了撤销栈。

### 取证

`onPropertyEdited()`（统一属性入口，600ms 合并）覆盖了标题/颜色/字号/加粗/绑定等字段，
但**另有 15 处属性面板 lambda 直接写控件字段、绕过了它**：

### 决定：不逐处补 `pushUndo()`，改统一入口

逐处补是 15 次重复劳动，而且**下次再加一个属性分组就又会漏一处**——这正是过去漏掉的机制。
改为新增 `markPropertyEdit()`（与 `onPropertyEdited` 同款 600ms 合并），

这个统一模式后面都接上它，共 15 处；同时删掉第七批在密码 lambda 里手写的那句
`pushUndo()`（统一入口后重复，会让撤销要多按一次）。

新增只读测试钩子 `controlsForTest()`（与 `serialIoThreadForTest` 等同风格），
让腿能断言「面板改完确实写回、撤销确实回退」，而不是靠间接现象猜。

### 腿与改坏自证

`designerPanelEditsAreUndoable`：添加子界面控件 → 从面板改圆角 → 断言写回 →
`undo()` → 断言回到基准值；并断言「改圆角确实改变了字段」（防空转通过）。

**改坏自证**：把 `markPropertyEdit()` 清空后重跑，该腿变红，失败点是
「撤销后控件不该消失」——因为编辑没压快照，`undo()` 直接撤回「添加控件之前」。
这比断言数值不等更能说明问题：它证明撤销栈里根本没有这次编辑的位置。还原后 63 passed。

### 两个我自己写错的断言（如实记录）

1. `QCOMPARE(cornerRadius, 0)` —— 子界面控件默认圆角是 **8**，不是 0。改为取控件自身
   默认值作基准，不写死常量。

属通信管理域，与设计器撤销栈不是同一套机制，单独一批做。

## 十、第九批：布局持久化字段成对性闸

### 先纠正一处我自己的错误陈述

上一批我说「剩下的都是控件种类，下一个值得补的是运行控制 / 运行状态 / OK-NG」——
**这是错的**。核实 `RuntimeControlType` 枚举：**24 项全部落地**，`RunControl`、
`OkNgCount`、`RunStatus` 都在里面。1:1 的结构层已经到顶，剩余的是导出工程包（用户暂缓）
与真机报文核对（挂起），都不是「补功能」能推进的。第十一节又核实出「FINS 参数面板」同样
已经存在，台账那条也是过时的。

据此改做对框架更有价值、且不需要真机的工作：**布局序列化字段成对性**。

### 为什么挑这个

`RuntimeInterface.cpp` 里布局靠手写 `toJson` / `fromJson` 存续，没有 schema。
「写出去但读不回来」的字段会让值在下次加载时静默消失，而我们已经踩过两次：

| 已修的实例 | 症状 |
|---|---|
| `cornerRadius` | 只在 `RunStatus` 分支写出，设计器却允许给 `SubInterface` 设 → 保存后变 0 |
| `subPassword` | 明文存储 + `!=` 直比 |

这两次都是人工发现的。同一形状的问题还有没有，靠再读一遍 3000 行不可靠。

### 审计结果：现存的不对称已经清零

新增 `tools/layout_field_pairing_gate.py`，机械比较三对 writer/reader 的键集合：

| 对 | writer | reader | read_only（保存后丢失） |
|---|---|---|---|
| `RuntimeControl` | 74 | 73 | **0** |
| `RuntimeInterfacePage` | 15 | 16 | **0** |
| `RuntimeInterface` | 10 | 10 | **0** |

唯一的 `write_only` 是 `RuntimeControl.type`：控件类型由 `runtimeControlTypeFromName()`
单独解析后作为参数传给 `controlFromJson`，所以 reader 里不出现 `o["type"]` —— 这是正确的。

键提取覆盖该文件用到的全部别名（`o`/`root`/`json`/`cv`/`bars`/`t`/`tabs`）与
`.value(QStringLiteral("k"))` 读取形式。刻意**不**把 `[=]` 这类语义猜测纳入判定。

|---|---|---|

`obj["k"]` 与 `obj[QStringLiteral("k")]`，读取还有 `.value(QStringLiteral("k"))`。
第一版只写了前者的 `obj["k"]` 形态，结果 12 对全部 `writer=0` —— **空扫描会假绿**，
这是我先看到「审计结果：现存的不对称已经清零」的原因之一，值得记一笔：
**扫描器报 0 时，要先确认它真的扫到了东西**。

白名单两处，各带原因：

## 十二、第十一批：寄存器工具条的地址空间与两个假 API

### 上一批的建议被自己否掉了

上批末尾我打算「把 DL 配置和 `release-registry.json` 也纳入成对性闸」。取证后**否决**：
流程面的键大量**跨函数流动**，机械闸会产生一堆必须靠白名单压掉的"误报"——

| 键 | 写出方 | 读取方 |
|---|---|---|
| `fixtures.hom/hasPose/...` | `FlowScene::extrasToJson` | `FixtureValidation::loadFixture`（另一文件） |
| 节点 `x/y` | `ProjectManager::sceneToJson` | `HalconNode::fromJson` |
| `w/h` | `NodeGroupItem::toJson` | `FlowScene::extrasFromJson` 读 groupJson |

白名单把每一条都列一遍之后，闸就只剩"我列过的都对称"这一句空话，反而给人虚假安全感。
**能机械判定才有价值**——判不了就不硬塞。

### 改做：`RegisterSpaceBar` 两处确定性缺口

**① 16 位地址空间没有上界**

`addAddressesInSpace()` 里 `const int addr = start + i;` 没有任何钳制。首地址 65532 + 8 个
会产出 65539，而协议层按 `quint16` 打包 → 越界值**回绕到低地址**，等于往**错误的寄存器**
写值。现场表现是「明明写 65539，结果改坏了 3 号寄存器」，几乎无法反查。

修法：超过 65535 的项跳过，并且**跳过数量必须在状态栏说清**（静默少加同样是坑）。
状态提示统一放进 `addAddressesInSpace()`，去掉按钮 lambda 里的覆盖文案——否则
「跳过 N 个越界地址」这条信息会被后一句「已补齐 N 个地址」直接抹掉。

**② `m_blankHidden` 只写不读，是个假 API**

`setBlankRowsHidden()` 里赋值 `m_blankHidden`，但这个成员**在全仓没有任何读取点**。
所以「隐藏空白行」开着的时候，再点「添加地址」，新增的空白行照样可见——开关形同虚设。
修法：新增行时若 `m_blankHidden` 为真则 `setRowHidden(row, true)`。

### 腿暴露出的第三个问题（不是我原本要找的）

写腿时连续三次访问违规，最后定位到一个**产品缺陷**而不只是夹具问题：

`QTableWidget::setItem()` 在**列不存在时会静默丢弃 item**。若表格还是 0 列，
每行 `insertRow` 都成功、`setItem` 全被丢掉，而 `added` 照数上报——
状态栏说「已补齐 6 个地址」，表里一行都没有。`added` 这个度量本身就是假的。

修法：进函数先 `if (m_table->columnCount() == 0) m_table->setColumnCount(1);` 自愈，
保证 `added` 与实际可见行数一致。腿里也显式给表格设列（真实场景由通信管理对话框建列）。

> 这个过程也值得记一笔：我一开始以为是腿的夹具写错，靠 `fprintf(stderr) + fflush`
> 直写才拿到真证据（`qWarning` 在 QTest 崩溃时被缓冲吞掉），最后发现夹具和产品代码
> 各有一处问题。**夹具碰巧绕过产品缺陷时，腿是绿的但产品是坏的**。

**改坏自证**：去掉地址上界判断后，`registerSpaceBarClampsAddressSpace` 立刻红
（`added` 由 6 变 8）。还原后 `CommWritebackTest` **68 passed**。

`RegisterSpaceBar` 的「清空」是否可撤销——需要先定撤销粒度（整表一次 vs 逐格），
且它属于通信管理域、与设计器撤销栈不是同一套机制。

## 十四、第十三批：RoundAbortSummaryTest 的 flaky 根因（含两次自我纠错）

## 十六、第十五批：收掉最后一个跨线程容器数据竞争

上一批按范围控制留下的挂账项：`RoundAbortSummaryTest` 里 `errors`（`QStringList`）
与 `nodeStates`（`QHash`）仍由 `Qt::DirectConnection` 的槽在 **FlowExecutor 工作线程**
写、主线程遍历，无显式同步。虽然现有 `exec.wait()` 让写大多先于读，但结构上仍是
数据竞争（UB），不能靠「碰巧没撞上」当正确。

### 实现

匿名命名空间新增 `ConcurrentDiag`：

| 方法 | 作用 |
|---|---|
| `addError()` / `setNodeState()` | `QMutexLocker` 保护写 |
| `snapshot()` | 一次加锁返回 `Snapshot{ errors, nodeStates }` 本地副本 |

读侧**只在开头取一次快照**，后续所有 `stateList` 构造、`QVERIFY2` 诊断文本、
`contains` / `value` 判断都读本地副本，**不持锁跑断言**（避免锁内执行测试宏导致
意外长临界区或提前 return 时锁状态复杂化）。

两条腿共 2 处 `errors` 声明、1 处 `nodeStates` 声明、3 处写 lambda、8 处读全部收口；
`grep \berrors\b|\bnodeStates\b` 后只剩 `ConcurrentDiag` 自己的成员与 `diagSnap.*`，
无裸容器引用。**业务断言一字未改**（这些容器只用于诊断文本，不是断言数据源）。

### 关于验证（如实说明局限）

这是**纯 UB 消除**：容器只承载诊断字符串与节点状态，挪走竞争不会让任何业务断言
从红变绿或反之，因此**没有行为腿能覆盖它，也做不出有意义的改坏自证**——
强行补一条「自己测自己辅助类」的腿反而是项目一直避免的空腿。
验证靠三层：代码审查确认全部读写点收口、`exe` 时间戳确认真编译
（单目标 target 是 `round_abort_summary_test`，不是测试套件名）、
`ctest -j4` 连跑 **10 次全绿** 确认没破坏行为。

## 十七、第十六批：脚本审批与执行器 wait 的互等（审核清单最后一项风险）

这是审核清单里唯一能导致「整窗无响应」的项。之前一直挂着「需产品拍板」，用户
2026-11-12 明确「项目未上线、需拍板的你决定」，故本批自行定案。

### 先说清性质：不是永久死锁，是**有界挂死 + 假报**

| 侧 | 位置 | 行为 |
|---|---|---|
| GUI | `MainWindow.cpp:5187` `sceneEx->wait(6000)`、`:4883` `ex->wait(left)`（最长 15s）、另有 4 处 | `QThread::wait()` **不泵事件** |
| Worker | `ScriptSecurityPolicy.cpp:248-250` | `Qt::BlockingQueuedConnection` **无超时**等 GUI 弹窗 |

互等成立：GUI 卡在 `wait()` 不处理事件 ⇒ 投递过去的弹窗**根本不会显示** ⇒
worker 永远等不到返回。6~15 秒后 `wait()` 超时返回，代码走
「流程未能在 N 秒内停止」分支。

现场看到的是一条与真实原因无关的提示，而**真正卡住的审批框从未出现**——
用户既不知道发生了什么，也无从操作。这比明显的死锁更难查。

### 修法（自行拍板）

工作线程侧改成 **queued 投递 + 两段有界等待**：

| 阶段 | 超时 | 语义 |
|---|---|---|
| ① GUI 接管 | `kGuiTakeoverTimeoutMs = 500` | 超时说明 GUI 被阻塞 ⇒ **fail-closed**（拒绝脚本） |
| ② 用户决定 | `kUserDecisionTimeoutMs = 300000` 兜底 | GUI 已接管后用户看多久都行（脚本全文可滚动，本就要时间） |

关键设计：
- **分两段而不是一次等完**——否则用户仔细看脚本超过超时就会被误判成 GUI 卡死。
- **超时一律「拒绝」而非放行**，安全语义不放松；拒绝不进同意缓存，下一轮仍会重新询问。
- 新增 `abandoned` 标志：worker 超时放弃后，GUI 稍后处理到这条投递时**不再弹窗**，
  避免「脚本明明没执行，却弹一个没人等的确认框」。
- 超时时输出 `qWarning` 说明原因（GUI 可能正阻塞在 `Execution::wait`），
  让现场能从日志判断，而不是只看到「流程未能停止」。

**GUI 侧未改**：`wait()` 仍是阻塞的。有了工作线程侧的有界返回，互等已不成立，
改 `wait()` 为异步会影响执行器回收时序，风险大于收益。

### 测试侧的一处必要改造

`script_security_test` 原本用 `QTEST_GUILESS_MAIN`——**没有 `QApplication`**，
于是 `requestConfirmation` 在 `qobject_cast<QApplication*>` 处直接「无头放行」，
审批路径根本测不到。故改为 `QTEST_MAIN`，并在 CMake 里显式 `Qt6::Widgets`
（不依赖 `vfp_core` 的传递链接）。其余 9 条腿不依赖 GUI，改后照常通过。

**腿** `approvalFailsClosedWhenGuiThreadBlocked`：worker 线程调审批，主线程
`QThread::msleep(1500)` 按住 GUI（远超 500ms 接管超时），断言审批**有界返回**且
**结果为拒绝**。收线程先于断言，避免断言提前 return 留下未 join 的线程。

**改坏自证**：把 `kGuiTakeoverTimeoutMs` 临时改成 3000（> 腿里的 1500ms），
腿立刻红：`FAIL! 'didReturn' returned FALSE`，耗时 3023ms 等满超时；还原后
`ScriptSecurityPolicyTest` 13 passed。（用 3000 而非 60s，是为了让 worker 能在
`wait(5000)` 内收尾，不留下跑着的线程被 delete。）

**验证**：全量构建 0 错误；`ctest -j4` 连跑 **10 次全绿**；六道闸与宿主 CI 全绿。

### 已知边界

用户接管后若 5 分钟内不作决定，仍按拒绝处理（兜底，不是交互预期）。
审批缓存仍是「会话级、按内容哈希」，改脚本必然换键重问——这条未变。

按用户要求，各批均**未出包、未打 tag**。
